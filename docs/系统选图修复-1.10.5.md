# 系统选图修复 · 1.10.5

## 发现与边界

- 旧版只读取 Intent.getData()，忽略仅由 ClipData 返回的 URI。以合成图片回调测试复现静默丢弃；不能据此断言用户小米手机一定采用这种回传形式。
- 旧版以内容哈希判重，发现同一图片已在附件表时直接退出，导致在同一笔记的另一个位置也无法再次插入。真实 Android DocumentsUI 选同一文件复现。
- 旧版插图后重建整篇编辑 DOM，不利于长文的滚动、光标和即时反馈。新版直接插入并将图片滚动到可见区域。
- 选图期间 Activity 可以被系统重建。旧版没有恢复编辑器与可靠回传确认；新版从该记录的本机草稿恢复，图片回传持久暂存并在草稿落盘后确认。

没有取得用户小米手机的运行日志，因此以上是已验证的代码缺陷与兼容性修复，不声称已在用户真机复现全部原因。

## 实现

1. 图片 URI 优先取 getData，缺失时取 ClipData 首项；未返回 URI 时提示重选。
2. 原生导入图片后，将元数据及独立 deliveryId 暂存于私有 SharedPreferences。图片仍是本机私有 JPEG，不上传给模型。
3. 页面正常回调或初始化恢复时，在串行插入队列里处理，按 recordId 只恢复对应草稿，不向另一条打开的记录插图。
4. 附件按内容哈希去重存储，但正文允许多处引用同一图片。deliveryId 与文件哈希分开：前者防重复回调，后者省空间。
5. deliveryId 随草稿保存，成功落盘后确认暂存回传。相同回传重试不会再次插入；用户主动再次选图会产生新的 deliveryId。
6. 不重建整篇 DOM，保留旧图片／段落间距，滚动显示新增图片。撤销重做及显式保存仍走原有流程。

## 验证

隔离 Android 30 模拟器、WebView 83、合成长笔记与图片，不使用用户笔记、轨迹或真实 Key：

- ImagePickerFlowTest：真实按钮 → 系统 DocumentsUI → 选择图片 → content resolver → 原生回调 → 显示 → 草稿落盘 → 保存重开。
- duplicate：在同一记录再次选择同一文件，正文出现两处图片，私有文件无需复制。
- clip：在真实系统选图流程后，额外注入 ClipData-only 回传，确认不再静默丢弃。
- recreate：系统选图打开时真正调用 Activity.recreate，选图后恢复长笔记及图片。
- ImageSpacingTest、DocumentEditorTest、DraftPreviewTest、DocumentSafetyTest、VisualEditorTest 与 Node 测试作回归。

这不替代小米真机验证；厂商图库、云端原图下载失败、损坏／超限图片仍可能报错，不应伪装成插入成功。
